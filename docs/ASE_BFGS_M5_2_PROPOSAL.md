实际交付、失败记录和未完成范围见[M5-2报告](../reports/g2-ase-bfgs-m5-2.md)。

## 目标和可证伪假设

在当前匹配的 Torch/DTK26.04 环境，以隔离 HIP 原型减少真实147/285维
FP64 full-eigensystem 的 Jacobi kernel 耗时，先验证正确性和收益，再决定接入产品。
不等待匹配26.10的Torch，不改BFGS的H更新、abs谱、步长、UnitCellFilter或Batch语义。

M5-1的285维B1分解中，GPU kernel占trace窗口97%，`syevj_offd_kernel`
累计52.15ms，其launch只有5个1024-thread block；B4通过grid.z批量执行，
同一kernel累计52.29ms，旋转更新成本随batch增加。当前封装与残差/正交守卫均
为亚毫秒级。假设更细的并行旋转/更新粒度能减少这类小批量kernel的耗时；
这是待验证假设，trace尚未证明寄存器、LDS或特定指令是根因，也不承诺加速倍数。

## 本阶段边界

1. 先写最小solver合同与CPU oracle。仅实对称FP64、LOWER、完整排序w/V、
   n147/285、B1/B4；B4增加不同矩阵，避免只验相同副本。明确输入保护、布局、
   current stream、收敛残差、最大迭代与非收敛报错；明确Torch行主序与内部布局
   的映射，不引入autograd/compile。
2. 在probes下开发HIP batched Jacobi原型并用当前Torch扩展接入；针对旋转/更新
   的并行粒度做单一方向实验。数值矩阵和全部迭代数学留在HCU，允许显式最终
   状态读取。保留现有rocSOLVER和Torch reference作为独立基线；不注册产品
   后端、不改变默认选择，不在失败时静默切换求解器。
3. 首先通过真实简并Hessian、解析/随机/近简并矩阵的谱、残差、正交、输入保护、
   负谱/零谱、未选三角污染、非默认stream及明确失败检查，再在隔离进程
   接入已有BFGS数学做ASE逐步/重启
   和147/285/147分组对照。不能只看最终能量或info=0。
4. 过数值门后，按M5-1相同设备/输入/FP64/完整检查比较三进程、每项预热后
   至少7样本；候选与原生rocSOLVER基线交替运行，单卡限时，不混入JIT或profiler。
   对两结构真实MPA-0 FIRE2→变胞BFGS做同配置对照，记录成功率、轨迹误差、
   求值次数、总时间；探针I/O与同步范围保持一致。

## 验收与退出条件

- 谱atol=2e-10/rtol=2e-11、相对方程和正交误差<1e-10，沿用现有ASE轨迹门；
  保留失败原子性与非收敛检查，不放宽容差或降精度获取性能。
- 保留候选的性能条件：相同输入的完整checked solver稳态中位数至少降低10%，
  跨重复运行可见，同时真实CSP总时间有可重复收益。数值或性能门未过，保留
  实验报告并停止接入；允许本阶段得到“候选不值得保留”的结论。
- 交付合同、可运行隔离原型、精确命令/退出码/误差/原始样本和候选结论。
  产品注册、通用规模支持、其他dtype、NVIDIA、多卡及生产支持另行确认。
